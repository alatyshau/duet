# Стратегия тестирования Duet

**Статус:** черновик (требует актуализации)

**Происхождение:** Написано ~260201 при проектировании Host. Содержит ценные принципы и рефакторинг-план, но объекты тестирования и стек частично устарели.

**Что актуально:**
- Принципы (секция 1) — универсальные, применимы ко всем компонентам
- Уровни тестов (секция 3) — пирамида: static → unit → integration → UI → E2E
- Организация тестов (секция 5) — именование, фикстуры, моки
- Метрики (секция 6) — flaky rate = 0, coverage как сигнал
- Рефакторинг для тестируемости (секция 7) — этапы A-D, DI, контракты

**Что устарело:**
- Объекты тестирования: знает только Host и ai-kit. Не знает про Backend (Python MCP server) и Extension (VS Code)
- Стек: рекомендует Playwright для Electron E2E — мы выбрали WebdriverIO + wdio-electron-service
- `packages/ai-kit` упоминается как Python-скрипты — скрипты переехали в Backend

---

## 1. Принципы

- **Тестируем поведение, а не реализацию**: тесты фиксируют контракт (что должно работать), а не внутреннюю структуру (как именно).
- **Пирамида тестов**: больше дешёвых unit, меньше дорогих e2e.
- **Детерминизм**: без зависимостей от сети/времени/окружения (или всё это стабилизируется через фикстуры и инъекцию зависимостей).
- **Скорость обратной связи**: "быстрые" тесты запускаются локально за секунды; "медленные" — в CI по расписанию/порогам.
- **Одна причина падения**: каждый тест либо проверяет один контракт, либо даёт диагностируемое сообщение об ошибке.

---

## 2. Объекты тестирования

> **Обновлено 260224.** Duet состоит из трёх компонентов — у каждого свои особенности тестирования.

### `packages/host` (Electron)

- **Main process**: управление окнами/треем/жизненным циклом, интеграции OS.
- **Preload**: мост API в renderer, безопасность (контракт доступных методов).
- **Renderer (React)**: страницы/компоненты, состояния, роутинг, UX-логика.
- **Unit-тесты есть** (15 тестов, vitest). E2E нестабильны — см. [topic_host_e2e.md](topic_host_e2e.md).

### `packages/backend` (Python)

- **HTTP API**: health check, CRUD для entities.
- **MCP tools**: timestamp, workspace_info, streams, projects, scan.
- **SQLite БД**: иерархия entities, миграции.
- **Тестов мало** — см. [topic_backend_e2e.md](topic_backend_e2e.md).

### `packages/extension` (VS Code)

- **TreeView**: ДЕЛА, КОНТЕКСТ — рендеринг иерархии.
- **Commands**: команды расширения (open, scan, etc).
- **WASM**: tree-sitter грамматики, упаковка в VSIX.
- **Unit-тесты есть** (vitest). E2E нет — см. [topic_extension_e2e.md](topic_extension_e2e.md).

## 3. Уровни тестов

### 1) Статические проверки (самые дешёвые)

- **TypeScript**: `tsc --noEmit` (Host, Extension).
- **Python**: `mypy`, `ruff` (Backend).
- **Lint/format**: ESLint + Prettier (TS), ruff (Python).

**Цель**: ловить ошибки раньше выполнения кода.

### 2) Unit-тесты (логика без UI/OS)

**Где особенно полезны:**
- Любая "чистая" логика: парсинг, валидации, преобразования данных, правила состояния, вычисления.
- Преобразование конфигов/настроек, работа со строками и путями.

**Критерии:** быстрые (< 100–200мс на файл тестов), без реального FS/сети/таймеров.

### 3) Интеграционные тесты (границы модулей)

**Примеры:**
- Host main process: бизнес-логика + адаптеры (через моки).
- Host preload: контракт экспорта API (список методов, сигнатуры).
- Backend: HTTP endpoints + MCP tools с реальной тестовой БД.
- Extension: TreeView data providers с моками backend API.

**Цель:** ловить ошибки склейки модулей, не включая полный e2e.

### 4) UI-тесты (renderer)

- Компонентные тесты React (рендер, состояния, обработчики событий) — Host.
- Снэпшоты — осторожно: только там, где структура реально стабильна и полезна.

**Цель:** уверенность в UX-логике (что пользователь видит и может сделать).

### 5) E2E (сквозные сценарии)

**Минимальный набор "золотых" сценариев (smoke) для каждого компонента:**

| Компонент | Smoke | Инструмент |
|-----------|-------|------------|
| Host | Запуск → окно → tray → backend lifecycle | WebdriverIO + wdio-electron-service |
| Backend | Запуск → health 200 → scan → streams | pytest + httpx |
| Extension | Активация → TreeView → команды → WASM | @vscode/test-electron |

**Цель:** проверить "как пользователь", но держать набор маленьким.

## 4. Стек инструментов

### JS/TS (Host + Extension)

- **Unit/Integration**: `vitest`
- **UI**: `@testing-library/react` + `@testing-library/user-event` (Host renderer)
- **E2E Host**: `WebdriverIO` + `wdio-electron-service` v9.2.1
- **E2E Extension**: `@vscode/test-electron`

### Python (Backend)

- **Unit/Integration**: `pytest` + `httpx`
- **Linting**: `ruff`
- **Type check**: `mypy`

### CI

- **GitHub Actions**, matrix: macOS + Windows + Linux (с xvfb для headless)
- Триггеры: `push` + `pull_request` по `paths: packages/<component>/**`

---

## 5. Организация тестов

- **Размещение**:
  - `packages/host/**`: `*.test.ts` / `*.test.tsx` рядом с кодом
  - `packages/extension/**`: `*.test.ts` рядом с кодом
  - `packages/backend/**`: `tests/` рядом с пакетной логикой
- **Именование**: "что делает" + "какое ожидание" (на уровне describe/it).
- **Фикстуры**:
  - Фикстуры данных — рядом с тестами (`fixtures/`), без неявных зависимостей.
  - Любые "текущие даты" — через инъекцию `clock`/`now()`.
- **Моки**:
  - Мокаем внешние системы (FS, сеть, Electron API, VS Code API), но не мокаем собственную бизнес-логику.

---

## 6. Качество и метрики

- **Coverage**: не как KPI "любой ценой", а как сигнал.
  - Цель на старт: покрыть unit-тестами наиболее рискованные/часто меняемые модули.
  - E2E покрытие — минимально, но стабильно.
- **Стабильность**:
  - Flaky rate = 0 (флейки считаем багом инфраструктуры тестов).
- **Время**:
  - Быстрый набор (lint+typecheck+unit) должен укладываться в минуты в CI и быть комфортным локально.

## 7. Рефакторинг для тестируемости

> План направлен на уменьшение "стоимости теста": чем меньше скрытых зависимостей и сайд-эффектов, тем проще и быстрее тестировать.

### Этап A — "Стабилизировать границы" (самый высокий ROI)

1. **Выделить чистые модули** (pure core) из кода, который напрямую трогает Electron API, Node FS/Path, время, окружение.
2. **Слой адаптеров**: `core/` (чистая логика) → `adapters/` (обёртки над Electron/Node/OS) → `composition root`.
3. **Инъекция зависимостей**: передаём зависимости параметрами, а не импортируем глобальные API.

**Результат:** unit-тесты пишутся на `core/`, интеграционные — на контракты адаптеров.

**Статус Host:** Частично реализовано — `src/core/` выделен (config, app-state, deploy, backend, apps, ai-clients). Adapters не формализованы.

### Этап B — "Убрать сайд-эффекты из импортов"

Любой модуль, который при `import` делает I/O, создаёт окна, читает FS — переводится в явные функции `init()`/`register()`.

**Результат:** тесты могут импортировать модули без "взрыва" окружения.

### Этап C — "Контракты между слоями"

- **Preload API как контракт**: один источник правды для списка методов + тест, что preload экспортирует именно его.
- **Renderer ↔ API**: facade для API-вызовов, UI тестируется без реальных вызовов.
- **Extension ↔ Backend**: контракт MCP tools (типы запросов/ответов).

**Результат:** меньше сквозных зависимостей, меньше e2e "ради всего".

### Этап D — "Тестируемый Backend"

1. Разделить "бизнес-логика" и "HTTP/MCP обёртка".
2. TestClient (FastAPI) для integration-тестов без реального сервера.
3. Тестовая БД с seed data для предсказуемости.

**Результат:** backend тестируется быстро, без поднятия процесса.

---

## 8. Анти-паттерны

- Не пытаемся с первого дня покрыть всё e2e.
- Не делаем coverage "ради процента".
- Не пишем тесты, которые зависят от реального времени/сети/внешнего окружения без строгой стабилизации.
