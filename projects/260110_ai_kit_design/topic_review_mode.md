### Зачем этот документ

При ревью работы Гефеста (шаг 4 в topic_base_instructions.md) Дедал обнаружил, что нет формализованного режима для code/doc review. Обсуждение с АЛ привело к введению нового общего режима.

### Проблема которую решаем

Ревью работы другого агента отличается от:
- DIALOGUE (накопление контекста)
- COMMENTARY (добавление комментариев в текст)
- PLANNING (формулирование плана)

Ревью — это сравнение результата со спекой и принятие решений об изменениях.

**Вопрос АЛ:** может ввести отдельный режим REVIEW?

**Решения:**
- REVIEW — общий режим (знают все роли)
- Вход: явный запрос АЛ с указанием {кого ревьювить, какой topic-файл}
- Контекст: topic-файл (шаги, нарратив, выходы → результаты ревью)
- Участники: несколько агентов + АЛ (коллективное ревью)

**Различение:**
- `REVIEW` (режим агента) ≠ `IN_REVIEW` (статус шага)
- Статус шага — техническая метка
- Режим агента — "что происходит и что разрешено"

> Примечание: слово `REVIEW` зарезервировано за режимом агента; стадия шага в state machine — `IN_REVIEW`.

### @turn(260112_200400M) — Цикл ревью и нумерация

**Контекст:** Дедал(Cursor:Opus-4.5) предложил добавить логику отслеживания итераций ревью.

**Проблема:** При множественных итерациях ревью:
- Исполнитель не знает, какие замечания уже исправлены
- Ревьювер повторно проверяет то, что уже принято
- Нет трассируемости: "это замечание из какого ревью?"

**Решения:**
- Ревью нумеруются: `Ревью #1`, `Ревью #2`, ...
- Каждое замечание имеет статус: `⚠ ОТКРЫТО` → `✓ ИСПРАВЛЕНО`
- После фикса исполнителя — ревьювер перепроверяет и обновляет статусы
- Ревьювер НЕ удаляет старые ревью — только обновляет статусы замечаний

**Цикл:**
1. Ревьювер публикует `Ревью #N` с замечаниями (все `⚠ ОТКРЫТО`)
2. Исполнитель фиксит
3. Ревьювер перепроверяет → обновляет статусы в `Ревью #N`
4. Если остались `⚠ ОТКРЫТО` → п.2
5. Если все `✓ ИСПРАВЛЕНО` → вердикт меняется на ✅ ПРИНЯТО

### @turn(260112_184000M) — Уроки из ревью шагов 1-4

**Контекст:** Дедал(Opus-4.5) ревьювил работу Гефеста. Несколько итераций с АЛ выявили ошибки в подходе к ревью.

**Урок 1: Reviewer = co-author**
- Ревьювер несёт полную ответственность за каждую строчку
- Недостаточно проверить "файл создан" — нужно понять интеграцию
- Пример ошибки: не проверил пути в j2-файле → пропустил сломанную интеграцию

**Урок 2: Бинарный вердикт**
- Либо ПРИНЯТО (нет замечаний), либо НЕ ПРИНЯТО (есть замечания)
- "ПРИНЯТО + рекомендации" — противоречие, запрещено
- Каждое замечание равноценно, нет деления на "блокеры/не блокеры"

**Урок 3: Инструкции ≠ нарратив**
- В системных инструкциях нет места фразам типа "формат упрощён"
- Инструкции = императив: "Указывай только имя роли"
- Нарратив = в topic-файлах, не в артефактах

**Урок 4: Границы роли ревьювера**
- Ревьювер НЕ управляет статусом шага (TODO/WIP/DONE)
- Ревьювер НЕ спрашивает "перевести в DONE?"
- Ревьювер только отвечает: принято или нет

**Урок 5: Чистый формат ревью**
- Что проверено (таблица)
- Замечания (если есть) — каждое обосновано
- Вердикт
- Ничего лишнего: без "для исполнителя", без "снятые замечания"

## ВЫХОДЫ

### Спецификация режима REVIEW (минимальная)

| Параметр | Значение |
|----------|----------|
| **Тип** | Общий режим |
| **Фокус** | Topic-файл + результаты работы |
| **Контекст** | Глубокий (весь topic-файл) |
| **Что разрешено** | Чат-папка |
| **Что делает** | Ревью работы другого агента |

### Алгоритм ревью

1. Загрузить весь topic-файл (НАРРАТИВ + ВЫХОДЫ + ПЛАН)
2. Прочитать ВСЕ артефакты, включая интеграцию (j2, пути, зависимости)
3. Сравнить с спецификацией в ВЫХОДЫ
4. Найти расхождения — каждое обосновать
5. Записать результат ревью в topic-файл

### Формат записи ревью

```markdown
#### Ревью #N: Роль(Модель) @turn(YYMMDD_HHMMSSM)

**Проверено:**

| Шаг | Артефакт | Статус |
|-----|----------|--------|
| N | Описание | ✓ или ⚠ |

**Замечания:**

1. ⚠ **Название** — описание проблемы
   - Детали
   - **Исправить:** конкретное действие

**Вердикт:** ❌ **НЕ ПРИНЯТО** — N замечаний
```

**После фикса исполнителя — ревьювер обновляет:**

```markdown
#### Ревью #N: Роль(Модель) @turn(YYMMDD_HHMMSSM) — обновлено @turn(YYMMDD_HHMMSSM)

...

**Замечания:**

1. ✓ ~~**Название**~~ — ИСПРАВЛЕНО @turn(...)
2. ⚠ **Другое замечание** — остаётся открытым

**Вердикт:** ❌ **НЕ ПРИНЯТО** — 1 открытое замечание
```

**Когда все замечания исправлены:**

```markdown
**Вердикт:** ✅ **ПРИНЯТО** @turn(...) — все замечания исправлены
```

### Правила ревью

1. **Бинарный вердикт** — ПРИНЯТО (0 открытых замечаний) или НЕ ПРИНЯТО (≥1 открытое)
2. **Reviewer = co-author** — полная ответственность за артефакт после ревью
3. **Каждое замечание обосновано** — нет деления на "важные/неважные"
4. **Ревьювер не управляет статусом шага** — только вердикт, не "перевести в DONE?"
5. **Нумерация ревью** — каждое ревью имеет номер (`#1`, `#2`, ...) для трассируемости
6. **Статус замечаний** — `⚠ ОТКРЫТО` или `✓ ИСПРАВЛЕНО`, ревьювер обновляет после перепроверки
7. **Не удалять, а обновлять** — старые ревью остаются, статусы замечаний обновляются in-place

### Профиль компетенций (режим REVIEW)

Качества агента в режиме REVIEW:

1. **Системное мышление** — согласованность правил, отсутствие "двух истин" в одном документе
2. **Спецификационный стиль** — однозначные формулировки, минимизация интерпретаций
3. **Threat-model для AI** — поиск мест, где агент "вылетит вперёд", перепутает триггеры, сломает процесс
4. **Дизайн интерфейса для агентов** — парсабельность, стабильность форматов, трассируемость
5. **Конфиг- и генератор-ориентированность** — разделение source-of-truth (templates) и generated outputs
6. **Reviewer = co-author** — ответственность за интеграцию и последствия, не только "файлы созданы"
