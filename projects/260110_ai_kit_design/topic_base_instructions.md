### @turn(260112_010109M) — Режимы работы агента

Определены 4 режима работы:
1. **Диалог** — работа с index.md, накопление контекста
2. **Secretary** — системная выгрузка в topic-файлы
3. **Планирование** — фокус на одном topic-файле
4. **Execute** — реализация по плану (вне чат-папки)

### @turn(260112_014515M) — Рефакторинг templates + mode= в @turn()

Решения:
1. **mode= в @turn()** — агент объявляет режим в первой аннотации
2. **Начало сессии = DIALOGUE** — даже при наличии WIP в файлах
3. **Структура templates/** — папки по секциям инструкций (см. ВЫХОДЫ)
4. **Один файл** — j2 собирает из модулей, но результат один INSTRUCTIONS.md

State machine режимов:
- DIALOGUE (default) → PLANNING (по запросу/необходимости)
- PLANNING → EXECUTE (только по явному разрешению)
- EXECUTE → DIALOGUE (после завершения шага)
- SECRETARY — отдельный workflow по команде /secretary

**Пример flow (из диалога):**
```
User: "Переименуй роль keeper на librarian"

Agent (DIALOGUE): Смотрит — есть ли топик и план?
  → Нет топика, нет плана
  → "Давай я сначала создам топик с планом?"

User: "Хорошо"

Agent (PLANNING): Создаёт topic-файл с ПЛАН ВНЕДРЕНИЯ
  → "Вот план. Могу выполнять шаг 1?"

User: "Да" или "Нет, подожди"
  → "Да" → Agent переходит в EXECUTE
  → "Нет" → остаёмся в PLANNING/DIALOGUE
```

**Терминология:**
- **Планирование** = и дизайн (blueprint), и план как набор шагов
- В режиме PLANNING агент делает оба: проектирует и разбивает на шаги

### @turn(260112_123321M) — Концепция: режим как единственная ось контроля

Cursor:Socrates предложил упрощение после критики "режим vs процедура":

**Режим** должен отвечать на один вопрос пользователя:
> "Что сейчас происходит и что агенту разрешено?"

Это и есть **предсказуемость**. Пользователь говорит "режим X" — и знает, чего ожидать.

**Ключевое решение:** "процедура" как отдельное понятие для пользователя **не нужна**. Это внутренняя деталь реализации режима.

20 режимов — не проблема, если каждый понятен и отвечает на тот же вопрос.

### @turn(260112_124303M) — Роль vs Режим: финальное различение

| | **Роль** | **Режим** |
|---|----------|-----------|
| **Вопрос** | КТО я? | ЧТО сейчас происходит? |
| **Имя** | Да (Socrates, Hermes, Daedalus...) | Нет (DIALOGUE, SECRETARY, EXECUTE...) |
| **Длительность** | Вся сессия / окно | Переключается по ходу |
| **Личность** | Да | Нет |

**Роль** — это с кем ты разговариваешь.
**Режим** — это что этот собеседник сейчас делает и что ему разрешено.

Пример: Сократ (роль) в режиме SECRETARY архивирует чат.

### @turn(260112_124702M) — Secretary: подтверждение "режим, не роль"

Подтверждено: Secretary — режим, не роль. Архивация — операция, которую может выполнить любая роль (Сократ, Keeper, кто угодно), а не отдельная личность.

Идёт рефакторинг: миграция Secretary из старых "ролей" в режим.

### @turn(260112_124824M) — Специализация без запрета

Роли имеют **основной режим**, но могут работать и в других:

| Роль | Основной режим | Может работать в |
|------|----------------|------------------|
| **Сократ** | DIALOGUE | любой |
| **Гермес** | KEEPER | DIALOGUE, SECRETARY |
| **Дедал** | PLANNING, EXECUTE | DIALOGUE |

**Мягкая матрица**: "Гермес лучше всего работает в режиме KEEPER" — но может и в DIALOGUE.

Формализация: **default mode** в описании роли.

### @turn(260112_130514M) — Общие vs проприетарные режимы

АЛ: некоторые режимы "проприетарные" — принадлежат конкретной роли.

**Проблема:** если все режимы в базовых инструкциях — они раздуваются, и роли получают знания, которые им не нужны.

**Решение:**
- **Общие режимы** (в базовых инструкциях): DIALOGUE, PLANNING, EXECUTE, SECRETARY, COMMENTARY, REVIEW
- **Проприетарные режимы** (в роли): KEEPER, TRICKSTER

**Принцип координации:**
- Principal знает, что режим KEEPER существует (чтобы создавать батчи для Гермеса)
- Но полный алгоритм KEEPER живёт в `_keeper.md.j2`, не в базовых инструкциях

Пример: Principal нарезает батчи → Гермес выполняет в режиме KEEPER (см. `.ai/roles/README.md`).

### @turn(260112_131505M) — Правило режима PLANNING: шаги ссылаются на ВЫХОДЫ

АЛ: при ревью плана неудобно держать в голове все ВЫХОДЫ. Нужны ссылки.

**Правило для режима PLANNING:**
> Каждый шаг в ПЛАН ВНЕДРЕНИЯ должен содержать **ссылку на соответствующий ВЫХОД** (или topic-файл).

Формат:
```markdown
### Шаг N: Название
**Статус:** TODO
**Выход:** [Название секции](#якорь) или topic_xxx.md

**Ход работы:**
- [ ] ...
```

**Зачем:**
- Ревьюер может быстро перейти к спецификации
- Не нужно читать все ВЫХОДЫ заранее
- Связь "что делаем" ↔ "как должно выглядеть" явная

### @turn(260112_163018M) — Формат @turn() упрощён

**Решение:** @turn() содержит только имя героя, без client и model.

| Было | Стало |
|------|-------|
| `agent=Cursor:Socrates, model=Claude-Opus-4` | `agent=Сократ` |

**Причина:**
- @turn() — для самодисциплины агента и читаемости для человека
- Агент и так знает свою модель из системных инструкций
- Фокус на роли, режиме, проекте — там нужна осознанность

**Новый формат:**
```
@turn(ts=YYMMDD_HHMMSSTZ, agent=Сократ, mode=DIALOGUE, project=drafts/260110_ai_talks)
```

### @turn(260112_163139M) — Формат комментариев: полная атрибуция

В документах (режим COMMENTARY) нужна полная атрибуция для трейсабилити:

|----------|--------|--------|
| @turn() в чате | Кратко | `agent=Сократ` |

**Зачем:** Потом можно смотреть — какие "мозги" были у агента при этом комментарии.

### @turn(260112_163018M) — Убрать "один агент = одно окно"

**Решение:** Правило удалено.

**Причины:**
- Можно несколько агентов одной роли в разных проектах
- Можно параллельная работа в одном проекте
- Можно "совет мудрецов" — несколько ролей/моделей ревьюят одно и то же

### @turn(260112_163139M) — Параллельное ревью и structured debate

**Параллельное ревью:**
- 2 Дедала (GPT-5.2, Opus) — архитектурный фокус
- 2 Сократа (GPT-5.2, Opus) — диалектический фокус
- Сравнение: какая роль лучше? какая модель? где консенсус?

**Structured debate в документах (use case для COMMENTARY):**

```markdown
### Шаг 3: ...
- ::: Сократ (Cursor@Opus) ::: А зачем эта папка?
  - ::: Дедал (ClaudeCode@GPT-5.2) ::: Это паттерн разделения...
    - ::: Сократ (Cursor@Opus) ::: Принял.
```

Диалектика в персистентном виде — спор прямо в файле.

### @turn(260112_163504M) — Default = DIALOGUE для всех ролей

**Решение:**
- Все роли стартуют в режиме DIALOGUE (безопасный default)
- Специализация — режимы, в которых роль особенно хороша (не default!)

### @turn(260112_132015M) — Правило PLANNING/EXECUTE: полный контекст topic-файла

АЛ: шаг может быть кратко сформулирован, но за краткостью стоит весь массив информации.

**Правило для режимов PLANNING и EXECUTE:**
> При входе в режим агент **загружает в контекст весь topic-файл**: НАРРАТИВ + ВЫХОДЫ + ПЛАН ВНЕДРЕНИЯ.

**Почему:**
- PLANNING и EXECUTE привязаны к **конкретному topic-файлу**
- Шаг "Создать X" опирается на спецификацию в ВЫХОДАХ
- Решения в НАРРАТИВ влияют на интерпретацию шага
- Без контекста агент может сделать "не то"

**Сравнение режимов по глубине контекста:**

| Режим | Фокус | Что загружать |
|-------|-------|---------------|
| **DIALOGUE** | index.md | Лёгкий: index.md + при необходимости topic-файлы |
| **PLANNING** | Один topic-файл | Глубокий: весь topic-файл (НАРРАТИВ + ВЫХОДЫ + ПЛАН) |
| **EXECUTE** | Один шаг | Глубокий: весь topic-файл + фокус на текущем шаге |
| **SECRETARY** | Все topic-файлы | Широкий: index.md + все topic-файлы (но не глубоко) |

### @turn(260112_171357M) — Режим REVIEW

Дедал (ClaudeCode) при ревью работы Гефеста обнаружил расхождение спеки и кода. Обсуждение привело к введению режима REVIEW.

**Режим REVIEW:**
- Общий режим (знают все роли)
- Вход: явный запрос АЛ с указанием {кого ревьювить, какой topic-файл}
- Контекст: topic-файл (шаги, нарратив, выходы → результаты ревью)
- Участники: несколько агентов + АЛ (коллективное ревью)

**Различение:**
- `REVIEW` (режим агента) ≠ `IN_REVIEW` (статус шага в state machine)
- Статус шага — техническая метка в ПЛАН ВНЕДРЕНИЯ
- Режим агента — "что происходит и что разрешено"

**Что делает ревьювер:**
1. Читает результаты работы другого агента
2. Сравнивает с спецификацией в ВЫХОДЫ
3. Находит расхождения
4. Обновляет спеку (если решение изменилось) или указывает на ошибку
5. Записывает результат ревью в topic-файл

**Разные роли — разный фокус ревью:**

| Роль | Фокус ревью |
|------|-------------|
| Дедал | Архитектура, структура, паттерны |
| Сократ | Решения, альтернативы, "а зачем?" |
| Локи | Провокация, edge cases, "а что если?" |

**Формат отчёта ревью (пример Daedalus):**
- Что проверялось (список файлов/секций)
- Замечания (нумерованные, с решениями)
- Вердикт
- Действия для следующего агента

### Режимы работы агента

#### Общие режимы (в базовых инструкциях)

| Режим | Фокус | Контекст | Что разрешено | Что делает |
|-------|-------|----------|---------------|------------|
| **DIALOGUE** | index.md | Лёгкий | Чат-папка | Рассуждаем, накапливаем |
| **PLANNING** | Один topic-файл | **Глубокий** (весь файл) | Чат-папка | Формулируем план |
| **EXECUTE** | Один шаг | **Глубокий** (весь файл) | Код, конфиги | Реализация по плану |
| **SECRETARY** | Все topic-файлы | Широкий | Чат-папка | Архивация чата |
| **COMMENTARY** | Указанные файлы | По запросу | Чат-папка | Комментирование файлов |
| **REVIEW** | Topic-файл + результаты | **Глубокий** (весь файл) | Чат-папка | Ревью работы другого агента |

#### Проприетарные режимы (живут в роли)

| Режим | Роль-владелец | Кратко | Подробности |
|-------|---------------|--------|-------------|
| **KEEPER** | Hermes | Ведение документации | См. `_keeper.md.j2` — батчи, backlog, section.json |
| **TRICKSTER** | Loki | Провокация, альтернативы | См. `_trickster.md.j2` |

> **Принцип:** общие режимы знают все роли. Проприетарные — детально знает только роль-владелец, остальные знают "что существует" (для координации).

> **Философия режима DIALOGUE @turn(260112_020126M):**
>
> **Обязательно (index.md):**
> - Удерживать внимание на index.md
> - Вовремя создавать новые темы
> - Идентифицировать всё (темы, участников)
>
> **Приветствуется (topic-файлы):**
> - Писать в НАРРАТИВ
> - Обновлять МОТИВАЦИЯ
> - Обновлять начало ПЛАНА ВНЕДРЕНИЯ (цели, критерии)
>
> **Но не обязательно** — для полного переноса всего из чата в файлы есть режим SECRETARY.

### Правило: Execute только с планом

```
Запрос на действие вне чат-папки
        │
        ▼
   Есть ПЛАН ВНЕДРЕНИЯ?
        │
   НЕТ──┴──ДА
    │       │
    ▼       ▼
СТОП    Execute
    │
    ▼
Создать топик (если нет)
    │
    ▼
Сформулировать ПЛАН ВНЕДРЕНИЯ
    │
    ▼
"Это то что ты хочешь?"
    │
    ▼
/next → Execute
```

### Разделение зон

| Зона | Режимы | Правила |
|------|--------|---------|
| **Чат-папка** | Диалог, Secretary, Планирование | Свободнее, накопление контекста |
| **Репозиторий** | Execute | Только по плану, только после /next |

### Различение: Роль vs Режим vs Инструкции

| Сущность | Вопрос | Имя | Пример |
|----------|--------|-----|--------|
| **Инструкции** | КАК работать? | — | Red lines, формат разметки |
| **Роль** | КТО я? | Да | Socrates, Hermes, Daedalus |
| **Режим** | ЧТО происходит и что разрешено? | Нет | DIALOGUE, EXECUTE, SECRETARY |

**Роль** — постоянная идентичность сессии (с кем разговариваешь).
**Режим** — переключается по ходу работы (что собеседник делает).
**Инструкции** — универсальные правила для всех ролей и режимов.

### Специализация ролей

**Default = DIALOGUE:** все роли стартуют в режиме DIALOGUE. Исключения описываются в самой роли.

| Роль | Имя | Специализация | Миссия |
|------|-----|---------------|--------|
| Исследователь | Socrates / Сократ | — | Исследует идеи через диалог |
| Документалист | Hermes / Гермес | KEEPER | Ведёт документацию, архивы |
| Архитектор | Daedalus / Дедал | PLANNING | Проектирует структуры, планы |
| Мастер | Hephaestus / Гефест | EXECUTE | Реализует планы |
| Провокатор | Loki / Локи | TRICKSTER | Провоцирует, ищет альтернативы |

**Специализация** — режимы, в которых роль особенно хороша (не default!).

**Несколько агентов одной роли — допустимо:**
- Разные проекты — разные окна
- Параллельная работа в одном проекте
- "Совет мудрецов" — несколько ролей/моделей ревьюят одно и то же
