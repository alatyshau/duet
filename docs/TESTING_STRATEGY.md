# Стратегия тестирования Duet

ЗАЧЕМ: Дать воспроизводимую систему тестов (быстрое доверие к изменениям, меньше регрессий, понятные “ворота” качества в CI) и план рефакторинга кода, чтобы эти тесты было реально писать и поддерживать.

КТО ИСПОЛЬЗУЕТ: Разработчики `packages/host` (Electron) и `packages/ai-kit` (скрипты/шаблоны), ревьюеры PR, CI.

---

## Принципы

- **Тестируем поведение, а не реализацию**: тесты фиксируют контракт (что должно работать), а не внутреннюю структуру (как именно).
- **Пирамида тестов**: больше дешёвых unit, меньше дорогих e2e.
- **Детерминизм**: без зависимостей от сети/времени/окружения (или всё это стабилизируется через фикстуры и инъекцию зависимостей).
- **Скорость обратной связи**: “быстрые” тесты запускаются локально за секунды; “медленные” — в CI по расписанию/порогам.
- **Одна причина падения**: каждый тест либо проверяет один контракт, либо даёт диагностируемое сообщение об ошибке.

---

## Объекты тестирования (области)

### `packages/host` (Electron)

- **Main process**: управление окнами/треем/жизненным циклом, интеграции OS.
- **Preload**: мост API в renderer, безопасность (контракт доступных методов).
- **Renderer (React)**: страницы/компоненты, состояния, роутинг, UX-логика.

### `packages/ai-kit` (Python-скрипты + шаблоны)

- **Скрипты**: генерация документов, работа с JSON-состоянием, форматирование timestamp.
- **Шаблоны**: стабильность генерации, отсутствие регрессий в структуре и обязательных секциях.

## Уровни тестов и “что именно проверяем”

### 1) Статические проверки (самые дешёвые)

- **TypeScript**: `tsc --noEmit` (строгий режим по мере готовности).
- **Lint/format**: ESLint + Prettier (или текущие аналоги в `packages/host`).
- **Зависимости**: отсутствие циклов/утечек модулей (опционально: madge/depcruise).

**Цель**: ловить ошибки раньше выполнения кода.

### 2) Unit-тесты (логика без UI/OS)

**Где особенно полезны:**
- Любая “чистая” логика: парсинг, валидации, преобразования данных, правила состояния, вычисления.
- Преобразование конфигов/настроек, работа со строками и путями.

**Критерии:** быстрые (< 100–200мс на файл тестов), без реального FS/сети/таймеров.

### 3) Интеграционные тесты (границы модулей)

**Примеры:**
- Main process: бизнес-логика + адаптеры (через моки), проверка “какие команды уезжают в Electron API”.
- Preload: контракт экспорта API (список методов, сигнатуры, правила доступа).
- Renderer: компонент + его зависимости (state/store/api) с тестовым окружением.

**Цель:** ловить ошибки склейки модулей, не включая полный e2e.

### 4) UI-тесты (renderer)

- Компонентные тесты React (рендер, состояния, обработчики событий).
- Снэпшоты — осторожно: только там, где структура реально стабильна и полезна.

**Цель:** уверенность в UX-логике (что пользователь видит и может сделать).

### 5) E2E (сквозные сценарии)

**Минимальный набор “золотых” сценариев (smoke):**
- Запуск приложения → открытие главного окна.
- Прохождение “setup” (если это основной пользовательский путь).
- Один-два сценария, которые ранее ломались (регрессионные якоря).

**Цель:** проверить “как пользователь”, но держать набор маленьким.

## Рекомендованный стек инструментов (без немедленных изменений репозитория)

> Ниже — целевой стек. Его добавление делается отдельным PR, по плану рефакторинга/внедрения.

### JS/TS (Host)

- **Unit/Integration**: `vitest` (быстро, дружит с Vite/TS).
- **UI**: `@testing-library/react` + `@testing-library/user-event`.
- **E2E**: `playwright` (в т.ч. режим Electron через `electron.launch`).

### Python (ai-kit)

- **Unit/Integration**: `pytest`.
- **Golden tests для генерации**: “эталонные” выходы + сравнение diff (с нормализацией timestamp/путей).

## Организация тестов (договорённость)

- **Размещение**:
  - `packages/host/**`: `*.test.ts` / `*.test.tsx` рядом с кодом или в `__tests__/` (выбрать один стиль и придерживаться).
  - `packages/ai-kit/**`: `tests/` рядом с пакетной логикой.
- **Именование**: “что делает” + “какое ожидание” (на уровне describe/it).
- **Фикстуры**:
  - Фикстуры данных — рядом с тестами (`fixtures/`), без неявных зависимостей.
  - Любые “текущие даты” — через инъекцию `clock`/`now()`.
- **Моки**:
  - Мокаем внешние системы (FS, сеть, Electron API), но не мокаем собственную бизнес-логику.

---

## Качество и метрики (чтобы стратегия была измеримой)

- **Coverage**: не как KPI “любой ценой”, а как сигнал.
  - Цель на старт: покрыть unit-тестами наиболее рискованные/часто меняемые модули.
  - E2E покрытие — минимально, но стабильно.
- **Стабильность**:
  - Flaky rate = 0 (флейки считаем багом инфраструктуры тестов).
- **Время**:
  - Быстрый набор (lint+typecheck+unit) должен укладываться в минуты в CI и быть комфортным локально.

## План рефакторинга, чтобы тестирование стало дешёвым

Ниже план направлен на уменьшение “стоимости теста”: чем меньше скрытых зависимостей и сайд-эффектов, тем проще и быстрее тестировать.

### Этап A — “Стабилизировать границы” (самый высокий ROI)

1. **Выделить чистые модули** (pure core) из кода, который сейчас напрямую трогает:
   - Electron API (`app`, `BrowserWindow`, `Tray`, `ipcMain`…)
   - Node FS/Path
   - время (`Date.now`)
   - окружение (`process.env`)
2. **Ввести слой адаптеров**:
   - `core/` (чистая логика, легко тестируется)
   - `adapters/` (обёртки над Electron/Node/OS, тестируются моком/контрактом)
   - `composition root` (единственное место, где всё “склеивается”)
3. **Инъекция зависимостей**:
   - Вместо “импортировали глобальный API и сразу вызвали” → передаём зависимости параметрами (например, `createApp(deps)`).

**Результат:** unit-тесты пишутся на `core/`, интеграционные — на контракты адаптеров.

### Этап B — “Убрать сайд-эффекты из импортов”

- Любой модуль, который при `import` делает I/O, создаёт окна, читает FS, регистрирует обработчики — переводится в явные функции `init()`/`register()` вызываемые из entrypoint.

**Результат:** тесты могут импортировать модули без “взрыва” окружения.

### Этап C — “Контракты между слоями”

- **Preload API как контракт**:
  - Один источник правды для списка методов (тип/интерфейс) + проверка, что preload экспортирует именно его.
- **Renderer ↔ API**:
  - Вынести работу с API в один клиент (facade), чтобы UI тестировать без реальных вызовов.

**Результат:** меньше сквозных зависимостей, меньше e2e “ради всего”.

### Этап D — “Тестируемая генерация документов (ai-kit)”

1. Разделить “парсинг/вычисление” и “запись файлов”.
2. Ввести режим “dry-run” (генерировать строки/структуры без записи).
3. Golden tests:
   - Эталонные входы (JSON/директории-фикстуры) → эталонные выходы (md/json)
   - Нормализация: timestamp, абсолютные пути, platform-specific разделители

**Результат:** регрессии в генерации ловятся автоматически и объяснимо.

---

## План внедрения (итеративно, без “большого взрыва”)

- **Шаг 0 — Инвентаризация рисков**: определить 5–10 критичных сценариев/модулей, которые чаще всего ломаются или наиболее дороги в регрессиях.
- **Шаг 1 — Быстрые ворота качества**: typecheck + lint + небольшой набор unit (первый “green bar”).
- **Шаг 2 — Выделение `core/`**: перенос 1–2 ключевых кусочков логики в чистые функции + тесты.
- **Шаг 3 — Контракт preload**: зафиксировать API и добавить тест, что экспорт совпадает.
- **Шаг 4 — Smoke e2e**: 1–2 сквозных сценария, максимально стабильных.
- **Шаг 5 — Расширение покрытия по боли**: добавлять тесты по следам реальных багов и изменений (bugfix-first, change-first).

---

## Что НЕ делаем (анти-паттерны)

- Не пытаемся с первого дня покрыть всё e2e.
- Не делаем coverage “ради процента”.
- Не пишем тесты, которые зависят от реального времени/сети/внешнего окружения без строгой стабилизации.
