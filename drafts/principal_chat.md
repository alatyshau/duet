### 💡 Точечные улучшения

1. **Создай "Конституцию" (`.ai/constitution.md`)**
* Вынеси туда повторяющиеся блоки: *Красные линии*, *Формат шапки (ЧТО/ЗАЧЕМ)*, *Алгоритмы патчинга*.
* В ролях оставь ссылку: "Соблюдай запреты из `constitution.md`". Это сэкономит токены и упростит поддержку.
> [ALA] Я не уверен что это полезно, т.к. увеличивает количество файлов которые надо вычитать для личности ИИ. Аргумент что это сэкономит токены мной не понят. С чего вдруг?

2. **Формализуй "Handoff" (Передачу работ)**
* Добавь в **Principal** обязанность выдавать не просто "план", а **Spec File** (мини-ТЗ).
* L6 Engineer должен начинать работу только при наличии утвержденного Spec File.
> [ALA] это можно но это надо обдумать, когда и в каких обстоятельствах это происходит. Нужна user story.
> [Claude] Spec File нужен для сложных фич. Для багфиксов и мелочей — оверкилл. Возможно: "если задача > 1 дня → Spec File".

### 🤖 Советы по новым ролям (Кратко)

1. **Product Owner (PO)**
* **Зачем:** Principal увлечен архитектурой, L6 — кодом. Кто-то должен думать о **Пользователе**.
* **Фокус:** Пишет `BUSINESS_PLAN.md`, User Stories, Acceptance Criteria. Приоритезирует фичи.
> [ALA] Я думал что BUSINESS_PLAN.md пишет Principal. Надо определить скоуп.. но в любом случае мы будем работать над этим документом и там решим чья это ответственность. Principal решает кто за что отвечает.
> [Claude] PO как отдельная роль — рано. Principal + человек покрывают продуктовую часть. Когда будет 10+ фич в бэклоге — тогда можно думать. 

2. **QA / Test Engineer**
* **Зачем:** L6 пишет "счастливые пути". QA пишет тесты, которые пытаются сломать систему.
* **Фокус:** E2E тесты, генерация корнер-кейсов, нагрузочное тестирование.
> [ALA] Мы пока не пишем тесты вообще. Но в будущем когда начнём — тогда начнём. Я ещё не решил по стратегии. Это сложный вопрос. Тестировать VS Code и Electron очень не просто. И у нас нет бюджета писать тесты на всё подряд.
> [Claude] Когда дойдём — начинать с `packages/core` (чистая логика, легко тестировать). UI тесты — потом.

3. **DevOps / SRE**
* **Зачем:** Если проект обрастет CI/CD, Docker, деплоем.
* **Фокус:** `github/workflows`, Dockerfile, скрипты сборки (build system).
> [ALA] Пока звучит как overenginering
> [Claude] Согласен. GitHub Actions для релизов уже есть (или будет). Отдельная роль не нужна — L6 справится.


**Итог:** Сейчас у тебя сильный "Engineering Core". Не хватает "Product Layer" (PO) и "Safety Layer" (QA).
